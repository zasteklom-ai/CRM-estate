# Усадьба·CRM — прототип CRM по образу amoCRM

Для бронирования загородных площадок: единое окно чатов площадок (Авито, ЦИАН, Яндекс Недвижимость,
Яндекс Путешествия, Spitti, Суточно.ру) + IP-телефония, автоматическое создание сделки и карточки
клиента, роли и права, админка источников.

Стек прототипа: Python 3 (только стандартная библиотека: `http.server` + `sqlite3`) + vanilla JS.
Никаких сборщиков и npm-зависимостей в рантайме — чтобы можно было открыть и пощупать сразу.

## Запуск

```bash
cd venue-crm
python3 server.py                      # http://localhost:8080  (CRM_PORT=9000 python3 server.py)
```

Демо-доступы (сидируются при первом старте):

| Логин | Пароль | Роль | Что видит |
|---|---|---|---|
| `admin` | `admin123` | Владелец | всё, включая админку |
| `olga` | `demo123` | Руководитель | все сделки, воронка, отчёты, без прав на пользователей |

Сброс демо-данных: `rm -f crm.sqlite3* && python3 server.py`.

## Модель данных (ядро)

```
sources(id, code, name, kind[chat|telephony], api_state, enabled, position, manager_id, note)
clients(id, name, phone, phone_norm, source_id, budget, people, km, criteria[], directions[],
        comment, external_ref, owner_id, created, updated)
deals(id, title, client_id, stage_id, source_id, owner_id, price, created, updated, last_in)
stages(id, name, sort, prob, color, outcome[win|lose|null])
messages(id, deal_id, chat_key, source_id, dir[in|out], author, text, created, unread)
calls(id, deal_id, client_id, phone, dir, status, dur, manager_id, recording, note, created)
users(id, login, name, phone, role, perms[json], active, salt, hash)   -- pbkdf2-sha256
activity(id, ts, user_id, action, entity, entity_id, data)             -- аудит
settings(key, value)  -- webhook_token, assign_rule, one_open_deal_per_client, telephony, company_name
```

Поля карточки клиента — ровно по ТЗ: **номер телефона, источник (из справочника), бюджет,
критерии поиска (мультивыбор: баня / бассейн / банкет / свадьба / близость к городу),
количество человек, направление от города (мультивыбор: север / юг / восток), удалённость от города, км**.

## Правило «новое сообщение или звонок → сделка + карточка»

Код: `inbound_message()` и `inbound_call()` в `server.py`. Последовательность:

1. нормализация телефона (`+7 (999) 111-22-33` → `79991112233`), поиск клиента по `phone_norm`;
2. нет клиента → создаётся карточка с источником и именем из сообщения; есть, но полей не хватает → добираются;
3. если `one_open_deal_per_client=1` и у клиента уже есть открытая сделка (этап без `outcome`) →
   сообщение дописывается в неё, дублей нет; иначе создаётся сделка на первом этапе;
4. ответственный: `assign_rule` = `round_robin` (кому меньше активных сделок) | `source` (ответственный
   источника из админки) | `manual` (не назначать);
5. сообщение/звонок кладётся в ленту, `unread+1`, сделка поднимается в списке, событие пишется в `activity`.

Повторный вебхук с тем же `chat_id` в открытую сделку не создаёт дубль — это проверка на
идемпотентность в `selftest.py` («no duplicate deal for same client»).

## Контракт входящих вебхуков

```http
POST /webhook/chat
X-Webhook-Token: <из Админка → Настройки>
{ "platform": "avito", "chat_id": "a1b2c3",
  "from": { "name": "Елена", "phone": "+7 926 555-11-22" },
  "text": "Ищем дом с бассейном на свадьбу, 60 человек, юг, до 40 км" }
```

```http
POST /webhook/call
X-Webhook-Token: <токен>
{ "event": "call_answered", "phone": "+7 916 123-45-67", "duration_sec": 214,
  "recording_url": "https://…/rec.wav", "manager_login": "marina",
  "note": "запрос на банкет 25 человек" }
```

Ответ: `{deal_id, deal_new, client_id, client_new, source:{code,name}, unread}`.

## Как подключать площадки (честно про API)

| Источник | Доступ к сообщениям | Что делаем |
|---|---|---|
| **Авито** | официальный Avito API для бизнеса: OAuth2, объявления, ответы на сообщения, статистика | храним токен, поллинг чатов + вебхук площадки, `chat_id` = `external_ref`; исходящие — через API-метод отправки |
| **Суточно.ру** | Partner API (брони, события) + синхронизация через channel-manager (Контур.Отель, Travelline, Spitti) | события броней как входящие; сообщения — из партнерского кабинета/channel-manager |
| **Spitti** | у них есть API/вебхуки по канал-менеджеру и мессенджерам | самый простой вариант: прокидываем их события в `/webhook/chat` |
| **Яндекс Путешествия** | партнёрский API отелей (брони, календарь, цены) | бронь = сделка; сообщения — через партнерский кабинет, при отсутствии API — ручной ввод + шаблон |
| **ЦИАН** | публичного API чатов нет; есть подменные номера (звонки падают на ваш номер) и личный кабинет | звонки идут через телефонию (устройство → `/webhook/call`), переписку — форвард на почту/бота и затем в вебхук |
| **Яндекс Недвижимость** | открытого API сообщений нет | форвардинг заявок (email/Telegram-бот) → `/webhook/chat`, либо договорное подключение |
| **IP-телефония** | Mango Office / UIS / Zadarma / чистый SIP: HTTP-callback по событиям вызова + REST на исходящий + записи | приём в `/webhook/call`, click-to-call из карточки, ссылка на запись в ленте |
| **Сайт / форма / бот** | ваш собственный канал | форма шлёт прямо в `/webchat/chat` с `platform: "website"` |

Для площадок без официального API «белых» путей два: **официальное партнёрское подключение**
(запрос в отдел партнёров площадки) или **передача канала через третьих** (channel-manager,
агрегатор мессенджеров типа Umnico). Ходить «руками» по личному кабинету площадки скриптом —
это нарушение пользовательского соглашения площадки и хрупкая интеграция, так делать не будем:
при смене вёрстки всё падает, а доступ к аккаунту могут заблокировать.

Шаблон адаптера: `integrations/adapters.py` — функция на источник приводит чужой payload к нашему
формату, плюс `send_chat_message()` (исходящие) и `norm_call()` (телефония).

## Права (10 атомарных, перекрывают роль)

```
view_all_deals   все сделки (иначе только свои)      manage_sources  источники чатов
edit_clients     правка карточек                     manage_users    пользователи и права
send_messages    ответ в чатах                       manage_stages   воронка
log_calls        звонки/click-to-call                 manage_settings настройки, телефония, токен
delete_records   удаление                           view_reports    дашборд
```

Роль задаёт профиль по умолчанию, дальше в админке у каждого пользователя можно точечно
снять/добавить любой пункт (матрица в Админка → Пользователи → «права»).
Права проверяются на сервере на каждом запросе — UI-скрытие это только удобство.

Гарды, которые уже работают: отключённый пользователь не может войти и его сессии убиваются;
нельзя удалить/отключить себя и владельца; нельзя удалить пользователя с активными сделками
(сначала передача); нельзя удалить источник/этап с данными — только отключить.

## Что это за уровень (и чем он не является)

Прототип проверяет сценарий: «заявка с любой площадки → карточка → воронка → отчёт».
В нём уже есть реальные вебхуки, авторизация, pbkdf2-пароли, права и аудит, но нет:
многопользовательской изоляции по клиентам (мультиаренда), очередей и ретраев для исходящих,
реальных OAuth-обменов площадок, SIP-софтфона в браузере, mobile-версии, миграций и бекапов.

## Дорога в прод (порядок действий)

1. **Неделя 1-2.** Опрос площадки: какие источники реально используются, какие поля карточки нужны
   бизнесу (сейчас — 7 полей из ТЗ), какая АТС провайдера уже есть.
2. **Адаптеры.** Реализуем `adapters.py` под живые токены: Авито (официальный API) →
   Суточно/Spitti → телефония. Для ЦИАН и Яндекс Недвижимости — согласуем канал (email-forward/бот).
3. **Стек.** PostgreSQL + миграции (Alembic/Flyway), FastAPI или Next.js + Prisma — схема БД
   переносится один в один, поля `criteria`/`directions` из JSON-строк в нормальные таблицы
   (`client_criteria(client_id, criterion)`), чтобы фильтр «свадьба + юг + до 40 км» работал индексом.
4. **Соответствия требованиям.** 152-ФЗ: телефон и имя — персональные данные → хранение в РФ,
   политика, согласие, журнал доступа, право на удаление; TLS; секреты в vault, а не в `settings`;
   rate-limit и подпись вебхуков (HMAC вместо статичного токена).
5. **Автоматизации.** Триггеры (заявка → задача «перезвонить за 15 минут», отсутствие ответа 2 часа →
   эскалация РО), шаблоны ответов, теги, повторные продажи (история заездов клиента).
6. **Отчётность.** Конверсия по источникам (Авито vs ЦИАН vs телефония) с распределением first-touch /
   last-touch — это главное, ради чего такая CRM затевается.

## Полезные команды

```bash
# входящее сообщение «как с Авито»
TOKEN=$(python3 -c "import sqlite3;print(sqlite3.connect('crm.sqlite3').execute("
         "'select value from settings where key=\"webhook_token\"').fetchone()[0])")
curl -X POST http://localhost:8080/webhook/chat -H "X-Webhook-Token: $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"platform":"avito","chat_id":"t1","from":{"name":"Тест","phone":"+79990001122"},"text":"банкет 20 человек, юг"}'

# то же самое без curl
python3 -c "import urllib.request,json;urllib.request.urlopen(urllib.request.Request( \
 'http://localhost:8080/webhook/chat',data=json.dumps({'platform':'avito','chat_id':'t2', \
 'phone':'+79990001123','text':'свадьба 60 чел, север до 30 км'}).encode(), \
 headers={'Content-Type':'application/json','X-Webhook-Token':'$TOKEN'}))"
```
